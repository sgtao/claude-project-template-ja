# verify：4 段で確かめる

## 1. 機械検査
- 仕様の点検：`python3 _tools/check_spec.py`
- 制作：SPEC.md の合格条件ごとの検査（テスト、計測、キーフレームの画像）を、すべて実行する
- 知的作業：`python3 _tools/check_ledger.py --doc <成果物> --units 01_sources/units.txt`。
  数値があれば、台帳と元データからコードで再計算する
- 専門作業：`python3 _tools/check_cases.py`（未実行を残さない）。スキルを作ったら `python3 _tools/check_skill.py <フォルダ>`
- **検査の検査**：このサイクルで足した検査は、わざと壊した入力（負例）で不合格になることを確かめる。
  検査の出力の形（キー名、件数の数え方）は、実物の出力を見てから書く。空振りして合格する検査は、合格条件の証拠にしない
- 不合格は直して再実行する。警告は 1 件ずつ見て、直すか、理由を付けて残す

## 2. 実物の通し
見本や単体の検査が通っても、実物でだけ落ちることがある。「完成」の前に必ず 1 回行う。
- 実物の入力 1 件（ユーザーが実際に使う形のもの）を、ユーザーが使うのと同じ手順（コマンド、スキル、画面）で最後まで通す
- 出た出力を、1 の検査にもかける。入力と出力は `04_evals/<MMDD-NN>_<話題>/` に置き、何をしたかを `README.md` に書く
- 対話でしか確かめられない動作（質問の回数、確認の出し方、画面の操作）は、
  `_templates/_MANUAL-CHECK.md` から `MANUAL-CHECK.md` を作り、ユーザーに手順と期待する結果を渡す。
  ユーザーが確かめるまでは「未検証」と書く

## 3. 独立した審査
`reviewer` サブエージェントを呼ぶ。渡すのは、成果物、SPEC.md・BRIEF.md・PLAYBOOK.md のどれか、資料の場所、役割だけ。
制作の経緯、自分の自己評価、PROGRESS.md は渡さない。

役割は、仕事の型で決め、始め方の観点を 1 つ足す。

| 型 | 役割 |
|---|---|
| 制作 | 初めて触るユーザー |
| 抽出 | 相手方の担当者、または査読者 |
| 生成 | 想定読者（授業なら生徒） |
| 統合 | 方法論の専門家 |
| 判断 | 反対役 |
| 専門作業 | その作業の熟練者（判断の基準の穴）と、初めてその作業をする担当者（手順書だけで行えるか） |

| 始め方 | 足す観点 |
|---|---|
| 後付け | もとからいる開発者：既存のルールやテストを壊していないか |
| 移行 | 移行元の保守担当：同等性の基準から外れた動作がないか |
| 複製して改造 | 複製元の作者：ライセンスの表示、変えないと決めた点が保たれているか |

指摘の扱い：
- 優先順位の高い順に直す。直さない指摘は、理由を `PROGRESS.md` に書く
- 「低」として先送りする前に、その指摘を実物の出力で確かめ、合格条件に関わらないことを確かめる
- 「高」を直したら、直した箇所と元の指摘だけを渡して、もう一度審査させる
- 不合格や指摘の原因を報告する前に、報告に使うのと同じパス・同じ手順で再現する。再現しないうちは「推定」と書く

## 4. 仕込み検査（審査が働いているかを確かめる）
最終の成果物を出す前に 1 回行う。知的作業では必ず、制作と専門作業では数値の仕様書・設定表・判断の基準があるときに行う。

```bash
python3 _tools/seed_errors.py seed --in <成果物か資料> --out /tmp/seeded.md --key /tmp/key.json --n 5
# reviewer に /tmp/seeded.md を審査させ、報告を /tmp/review.md に保存する（key.json は渡さない）
python3 _tools/seed_errors.py score --key /tmp/key.json --report /tmp/review.md
```

検出が 8 割未満なら、審査の役割の指示か、渡す資料を見直して、やり直す。
仕込んだ写しは `/tmp` に置き、リポジトリの成果物と混ぜない。

## 報告
合格条件を 1 つずつ「合格／不合格／未検証」で並べ、未検証には理由を書く。省いた段があれば、段と理由を書く。
すべて合格で、実物の通しと仕込み検査も済んだときだけ「完成」と書く。
